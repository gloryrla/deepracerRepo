## ⚠️ 방향 불일치 — 평가 결과가 무의미해지는 함정 (2026-08-20 발견)

**A to Z Speedway는 시계/반시계 양방향을 모두 지원한다.** 콘솔에서 확인:

```
COUNTER_CLOCKWISE : checked=false  disabled=false
CLOCKWISE         : checked=true   disabled=false   <- 기본값
```

7개 모델 전부 **기본값인 CLOCKWISE로 학습**됐다. 그런데 Evaluation을 반시계로 돌리면
**모델이 한 번도 본 적 없는 트랙을 달리게 된다.**

### 왜 치명적인가

정책은 `카메라 픽셀 -> 행동` 함수다. 방향을 뒤집으면:

1. **카메라 화면이 전혀 다르다.** 학습한 이미지 분포 밖이라 입력 자체가 미지의 값이다
2. **코너 순서가 역순이다.** 헤어핀이 나오는 타이밍이 완전히 달라진다
3. **선회 방향이 반대다.** 학습 때 왼쪽으로 꺾던 지점에서 오른쪽으로 꺾어야 한다

성능이 조금 나빠지는 게 아니라 **거의 전면 실패**한다. A-v1의 12회 이탈은 이것으로
충분히 설명된다.

### 조치

- **재학습 불필요.** Evaluation을 **Clockwise**로 다시 돌리면 된다
- **평가 방향을 확인하기 전에는 캡을 내리지 마라.** 방향 불일치가 원인이라면
  속도를 내리는 것은 시간 낭비다

### 미해결 (최우선)

**본선 주행 방향이 시계인가 반시계인가.** 양방향 모두 가능한 트랙이므로 우리는
기본값을 그대로 쓴 것이지 확인해서 고른 게 아니다.
**반시계가 정답이면 7개 전부 재학습해야 한다.**

### 앞선 진단 두 개를 정정한다

**1. A-v1의 12회 이탈은 캡 2.2가 과했기 때문이 아니다.** 시계로 다시 평가하니
5/5 완주, 최고 8.704초가 나왔다. 원인은 방향 불일치였다. 캡을 1.5로 내리라는
권고는 철회한다.

**2. "A는 가장 빨리 수렴하고 E는 상한이 높다"는 전제도 절반만 맞았다.** E-v1은
상한만 높은 게 아니라 편차도 가장 작았다(0.086초 대 A-v1 1.003초). 정보량이 많은
보상이 수렴을 방해할 수 있다는 우려는 이 트랙에서는 나타나지 않았다.
