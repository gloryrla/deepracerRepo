# 발표 대본 — 우리 팀이 이 전략으로 간 과정

> 코드와 함께 설명하기 위한 대본. 각 절에 **말할 내용**과 **보여줄 코드**를 짝지었다.
> 예상 소요 5~7분. 시간이 짧으면 2·4·5절만 해도 이야기가 성립한다.

## 0. 한 줄 요약 (먼저 말하고 시작)

> "저희는 이론적으로 최적인 경로를 계산해서 학습시켰고, 시뮬레이터에서 가장 좋은
> 기록을 냈습니다. 그런데 실차에서 그 모델이 가장 먼저 탈락했습니다.
> 오늘 말씀드릴 건 **왜 그랬는지**와 **그래서 무엇을 선택했는지**입니다."

## 1. 첫 접근 — 좌표

**말할 것**

트랙이 미리 정해져 있었습니다. 그래서 **인코스, 즉 이동 거리를 줄이는 것**이
가장 중요하다고 판단했습니다. 좌표별 조향각과 그에 맞는 속도를 연구했습니다.

곡률 균등화(K1999) 알고리즘을 1500회 적용해 최적 궤적을 직접 계산했습니다.

| 지표 | 센터라인 | 계산된 라인 |
| :--- | ---: | ---: |
| 길이 | 16.635 m | **15.409 m (−7.4%)** |
| 최소 코너 반경 | 0.61 m | **0.79 m (+30%)** |

거리를 7.4% 줄였고, 각 점의 목표속도까지 물리로 계산해 붙였습니다.
코너 한계속도 `sqrt(횡가속도 한계 / 곡률)`을 구한 뒤, 앞뒤로 가감속을 전파해서
**"다음 코너를 위해 지금 감속해야 한다"를 좌표에 새겨 넣었습니다.**

**보여줄 코드** — `reward_functions/lane_e_trajectory.py`

```python
# 궤적에서 가장 가까운 점을 찾고, 그 점이 요구하는 속도를 함께 가져온다
for px, py, pv in TRAJ:
    ...
# 위치항 x 속도항. 곱이므로 둘 다 맞아야 점수가 나온다 (AND)
reward = exp(-ALPHA * (dmin/tw)**2) * exp(-BETA * abs(speed - v_target))
```

곱셈인 것이 핵심입니다. 더하기로 하면 "라인은 완벽한데 속도가 엉망"인 주행이
절반 점수를 받고, 그런 정책은 **최적 경로 위를 기어가는 차**로 수렴합니다.

## 2. 컴퓨터공학적 병목 — 2시간 30분

**말할 것**

여기서 문제를 만났습니다. **학습 1회에 약 2시간 30분**이 들었습니다.
훈련 1시간, 검증 및 실행 1시간, 기타 시간까지요.

**한 번 만든 모델이 실패하면, 혹은 파인튜닝하려면 매번 2시간 30분입니다.**
하루에 3~4번밖에 못 돕니다. **순차적으로 개선하는 방식은 성립하지 않았습니다.**

그래서 전략을 바꿨습니다. **처음에 가설을 최대한 벌려놓고 병렬로 검증하기로**
했습니다.

| 레인 | 가설 | 방식 |
| :--- | :--- | :--- |
| B | 최적 궤적이 랩타임을 만든다 | **좌표** |
| C | 감가속 타이밍이 랩타임을 만든다 | 곡률 |
| E | 위치와 속도를 함께 주면 가장 빠르다 | **좌표 + 속도** |
| A | 단순·안정이 이긴다 | 중앙선 |
| D | 실차 일관성이 이긴다 | 중앙선 + 워블 억제 |

**좌표를 학습시킨 3개(B·C·E)와 안정적으로 중앙을 찾는 2개(A·D)로 나눴습니다.**

> 이 결정이 결과를 구했습니다. **전부 좌표로 갔으면 실차에서 아무것도 못
> 건졌습니다.**

## 3. 시뮬레이터 결과 — 가설이 맞았다

**말할 것**

| 레인 | 평균 | 탈선 | 편차 |
| :--- | ---: | ---: | ---: |
| **E (좌표 + 속도)** | **7.473초** | 0 | **0.086** |
| C (곡률) | 9.283초 | 0 | 0.408 |
| A (중앙선) | 9.501초 | 1 | 1.003 |
| D (중앙선 + 워블) | 9.698초 | 1 | 1.104 |

**정보량이 많은 보상이 그대로 순위였습니다. E > C > A > D.**
최소 거리로 과적합하게 학습시킨 E가 가장 좋았습니다. 편차도 0.086초로 가장
작았습니다.

여기까지는 완벽했습니다.

## 4. 실차 — 순위가 뒤집혔다 (이 절이 핵심)

**말할 것**

실차에서 **좌표 기반 모델이 트랙 반대쪽으로 계속 이탈**했습니다.
그리고 **시뮬에서 가장 느렸던 D가 유일하게 안정적으로 완주**했습니다.

가장 먼저 학습 부족을 의심했지만 아니었습니다. **E는 60분 학습에 시뮬에서
탈선 0회, 편차 0.086초**입니다. 미수렴이면 시뮬에서 먼저 드러납니다.

원인은 두 가지였습니다.

**첫째, 여유폭이 카메라 레이턴시를 못 버텼습니다.**

최적 경로는 흰선에서 0.180 m 떨어져 달립니다. 센터라인은 0.439 m입니다.
카메라 지연 동안 차는 계속 굴러가므로 그만큼 늦게 반응합니다.

| | 지연 100 ms · 2.0 m/s = **0.20 m 밀림** |
| :--- | :--- |
| 최적 경로 | 여유 0.180 m 의 **111% — 초과** |
| 센터라인 | 여유 0.439 m 의 46% |

**지연 100 ms만 되어도 최적 경로의 여유가 전부 사라집니다.**
0.180 m는 시뮬레이터에서는 충분한 값이었습니다. **시뮬에는 지연이 없기
때문입니다. 저희는 지연이 없는 세계에 맞춰 여유폭을 설계했습니다.**

**둘째, 이게 더 근본적입니다. 보상이 요구한 과제 자체가 달랐습니다.**

| | 센터라인 | 좌표 |
| :--- | :--- | :--- |
| 정책이 풀어야 할 문제 | **차선을 화면 중앙에 놓기** | **내가 트랙의 몇 번째 지점인지 알아내고 거기서 인쪽에 붙기** |
| 필요한 능력 | 국소 반응 | **전역 자기위치 추정** |

좌표 보상은 정책에게 **자기위치 추정**이라는 훨씬 어려운 문제를 강요합니다.
그리고 정책이 그걸 푸는 수단은 카메라 픽셀뿐이라, **시뮬레이터의 배경과 텍스처
같은 시뮬 고유 단서를 외워서** 해결합니다. **실제 트랙에는 그 단서가 없습니다.**

센터라인이 요구하는 "차선 경계가 화면 어디 있나"는 실차에도 그대로 있습니다.
그래서 전이됩니다.

> **"보상에 정보를 많이 주면 좋다"가 시뮬에서는 맞고 실차에서는 틀린 이유가
> 이것입니다. 정보가 많은 보상은 전이되지 않는 능력을 요구했습니다.**

**보여줄 코드** — 두 파일을 나란히

```python
# 좌표 방식 (lane_e_trajectory.py) — 절대 위치가 필요하다
for px, py, pv in TRAJ:            # 110개 절대 좌표
    d = (x - px)**2 + (y - py)**2

# 채택한 방식 (final_d_speedup_clone.py) — 좌표가 한 줄도 없다
reward = math.exp(-4.0 * (d / tw) ** 2)   # d = distance_from_center
```

**최종 파일에는 좌표가 한 줄도 없습니다. 그게 채택된 이유입니다.**

## 5. 그래서 D로 고정하고, 낼 수 있는 최고를 찾았다

**말할 것**

대회 환경에서는 **D로 고정**하고, 이 모델로 낼 수 있는 **최고 속도와 조향각**을
찾기로 했습니다.

**커브에서 너무 날아가서 각도별로 또 만들었습니다.** 그리고 **20도일 때 커브를
가장 잘 소화한다**는 것을 밝혔습니다.

처음엔 각도를 더 키우면 안정적으로 코너링할 거라고 추측했습니다. **틀렸습니다.**

| 시도 | 결과 |
| :--- | :--- |
| 25도, 30도 | **바퀴가 헛돌았다** |
| 큰 각도 액션 존재 | **직진에서 좌우로 왔다갔다하며 잃는 시간이 더 컸다** |

물리로 계산해도 같습니다. `R = 축간거리 / tan(조향각)`이므로:

| 조향각 | 회전반경 | 한계속도 |
| ---: | ---: | ---: |
| 14도 | 0.662 m | 1.97 m/s |
| **20도** | **0.453 m** | **1.63 m/s** |
| 30도 | 0.286 m | **1.30 m/s** |

**조향각을 키우면 회전반경이 작아져서 한계속도가 오히려 내려갑니다.**
30도는 1.30 m/s를 넘으면 어떻게 꺾어도 밀려나갑니다. "바퀴가 헛돈다"가
정확히 이것이었습니다.

**그래서 20도 이상은 아예 못 가게 설정했습니다.** 그리고 **그 각도에서는 속도를
낮추고, 직선 구간에서는 속도를 올렸습니다.**

**보여줄 것** — 최종 액션 스페이스

```
 -20/1.30  -14/1.60   -8/2.00   -3/2.30    0/2.60
   3/2.30    8/2.00   14/1.60   20/1.30    0/2.00
```

**조향각이 커질수록 속도가 내려갑니다. 위 물리 표를 그대로 따라갑니다.**
`20/1.30`은 한계 1.63보다 낮게 잡아 실차 접지력이 가정보다 나쁠 경우를
흡수했습니다.

**보여줄 코드** — 워블 억제

```python
rate = abs(steer - PREV['steer'])   # 조향 변화율
if rate > 15:  reward *= 0.5
elif rate > 8: reward *= 0.8
```

시뮬레이터는 **서보 지연과 타이어 슬립을 모델링하지 않습니다.** 조향을 좌우로
튕기는 정책도 시뮬에서는 멀쩡해 보이지만 실차에서는 접지를 잃습니다.
그래서 **보상에서 직접 뺐습니다.**

## 6. 학습 밖에서 성적을 올렸다

**말할 것**

학습 1회가 2시간 30분인데 **스로틀 배율 변경은 즉시 반영되고 1회 주행은 수십
초**입니다. 그래서 모델을 고정한 뒤 **같은 모델에서 배율을 2% 단위로 올려가며
레인을 이탈하지 않는 최대 속도선을 찾았습니다.**

| 배율 | 결과 |
| :--- | :--- |
| 60~61% | 완전 주행 |
| 62% | 이탈 없으나 살짝 걸침 |
| 63% | 코너 안정권 |
| **64%** | **이탈 1회 발생** |

**코너 안정 상한 62~63%를 확정했습니다.**

여기서 중요한 걸 발견했습니다. **장소를 옮기니 배율 척도가 달라졌습니다.**
이전 장소의 75%가 새 장소의 65%였습니다. 노면 마찰과 배터리 상태가 바뀌면
배율-속도 관계가 이동합니다. **측정값을 그대로 가져올 수 없어서 스윕을 처음부터
다시 했습니다.**

그리고 마지막으로 **랩 전체를 하나의 배율로 묶지 않았습니다.**

```
출발 75%  ->  코너 진입 전 62%  ->  코너 통과  ->  즉시 75% 복귀
```

**가장 느린 구간이 랩 전체의 상한을 결정하는 문제를, 구간을 나눠서 풀었습니다.**
출발 위치도 카메라 기준 가장 뒤로 옮겨 가속 거리를 확보했습니다.

## 7. 마무리

**말할 것**

> 저희가 얻은 건 기록보다 **왜 그렇게 됐는지**입니다.
>
> 이론적으로 최적인 경로는 **지연이 없는 세계에서만 최적**이었습니다.
> 실차에는 지연이 있고, 그 세계에서는 **여유폭과 전이되는 단서**가 이깁니다.
>
> 그리고 이걸 알아낸 이유는 **처음에 가설을 벌려놓고 병렬로 검증했기**
> 때문입니다. 전부 좌표로 갔으면 아무것도 못 건졌습니다.
>
> 과적합이 생기지 않는 선에서 여러 시간대에 여러 모델을 돌렸고,
> 가장 인상 깊었던 건 **경기 트랙이 이미 있으니 최소 거리 좌표를 찾아 거기
> 가까울수록 점수를 주는 함수를 설계한 것**이었습니다.
> 그게 현실에서 실패했고, **타협해서 중앙선을 따라가는 것이 가장 낫다**는 걸
> 찾았습니다.

## 예상 질문과 답

**Q. 왜 좌표 방식을 더 잘 튜닝해보지 않았나요?**
> 시도했고 오히려 나빠졌습니다. 좌표를 추가 학습시킨 시도는 레이턴시 문제가
> 재발했습니다. 이건 좌표를 더 정확히 계산해서 해결되는 문제가 아니라
> **접근 자체의 성질**입니다. 절대 위치 추정이라는 전이되지 않는 능력을
> 요구하기 때문입니다.

**Q. 학습을 더 오래 돌렸으면 됐을까요?**
> 아닙니다. E는 60분 학습에 시뮬 탈선 0회, 편차 0.086초입니다. 미수렴이면
> 시뮬에서 드러납니다. 학습의 문제가 아니라 시뮬-실차 격차입니다.

**Q. 조향각을 더 키우면 코너를 더 잘 돌지 않나요?**
> 반대입니다. `R = 축간거리 / tan(조향각)`이므로 각도를 키우면 회전반경이
> 작아지고 한계속도 `sqrt(0.6g·R)`가 **내려갑니다.** 30도의 한계는 1.30 m/s로
> 20도의 1.63 m/s보다 낮습니다. 실차에서 바퀴가 헛돈 게 이것입니다.

**Q. 트랙이 바뀌면 이 모델을 다시 학습해야 하나요?**
> 최종 모델은 **좌표를 쓰지 않고 트랙 폭 상대값만 씁니다.** 그래서 코드를
> 수정할 필요가 없습니다. 반대로 좌표 방식은 절대 좌표라서 다른 트랙에서는
> 아스팔트 밖에 보상을 주게 됩니다. **범용성도 센터라인 쪽이 높습니다.**

**Q. 주행 방향은 어떻게 정했나요?**
> 이게 저희가 크게 배운 부분입니다. A to Z Speedway는 양방향 모두 선택
> 가능한데 처음에 기본값을 확인 없이 썼습니다. 같은 모델을 방향만 바꿔
> 평가하니 **8.7초와 39.5초, 4.5배 차이**가 났습니다. 정책은
> `카메라 픽셀 -> 행동` 함수라서 방향을 뒤집으면 학습한 적 없는 입력이
> 됩니다. **방향은 기본값을 쓰는 항목이 아니라 가장 먼저 확인할 항목입니다.**
